# 多领域采集与独立关系重建设计

## 目标

让多领域数据采集安全排队完成，并避免每次小批量采集后都执行耗时数小时的全库关系重建。

## 当前问题

`.github/workflows/crawler.yml` 需要保证所有导入写入安全串行，避免不同领域同时写入造成竞争。每次采集结束后还会无条件重建全库关系和人才评分；该步骤已经多次达到三小时上限，而实际采集通常在几分钟内完成。

## 设计

### 数据采集工作流

- 保留现有 `max`、`keywords` 和 `domain` 输入，避免改变现有调用方式。
- `crawler.yml` 只运行公开研究数据采集和入库，不再自动执行关系重建。
- 使用固定全局并发组，所有导入任务安全排队，防止不同领域的并发写入互相竞争。
- 继续使用现有 `SUPABASE_DB_URL` Secret，不新增凭据或数据库权限。

### 关系重建工作流

- 新增独立的手动工作流 `rebuild-relationships.yml`。
- 工作流复用现有依赖安装、数据库 Secret 校验和 `rebuild_relations_and_scores()` 入口。
- 使用固定全局并发组，确保任何时刻只有一个关系重建任务。
- 关系重建由管理员在一批领域采集全部结束后手动运行一次。

## 数据流

1. 管理员为一个或多个领域启动采集任务。
2. 采集任务按全局并发组排队，依次抓取并增量写入 Supabase。
3. 每个采集任务在导入完成后结束，不等待全库关系计算。
4. 一批采集全部完成后，管理员手动启动一次关系重建。

正在运行的旧工作流任务固定使用其启动时的提交版本，本次修改不会改变或中断该任务。

## 失败与恢复

- 单个领域采集失败只影响该领域，可单独重试。
- 全局串行降低跨领域重复写入和数据库锁竞争风险。
- 关系重建失败不会回滚已成功写入的人才、论文和机构数据，可独立重试。
- 工作流继续保留三小时超时作为失控保护；本次不修改关系构建算法本身。

## 验证

- 解析两个 YAML 文件，确认语法有效。
- 运行仓库现有的工作流/仓库守卫测试。
- 检查 `crawler.yml` 不再调用 `rebuild_relations_and_scores()`。
- 检查独立关系重建工作流包含 Secret 校验、依赖安装、固定并发组和现有重建入口。
- 推送后在 GitHub Actions 页面确认两个手动工作流均可见；用多个领域的小批量任务验证导入会安全排队并依次完成。

## 非目标

- 不改变采集关键词、去重逻辑、数据库结构或前端页面。
- 不优化关系重建算法；性能优化作为后续独立任务。
- 不自动判断一批采集何时全部结束，关系重建仍由管理员明确触发。
